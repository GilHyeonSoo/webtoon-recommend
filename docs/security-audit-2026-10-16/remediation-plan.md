# 보안 취약점 보완 실행 계획

작성일: 2026-10-16 (Asia/Seoul)

우선순위는 **현재 추천 API의 과부하 방어 → 외부에 노출된 크롤러의 관리 기능 차단 → 계산·수집 구조 개선 → 배포 환경 검증**이다. 앞선 보고서의 F01~F07, C01~C02를 모두 대상으로 한다. 이 문서는 계획이며, 아직 코드 수정·설정 변경·배포를 실행하지 않았다.

현재 추천 서버는 로컬 JSON을 읽으며 크롤러/Supabase를 사용자 요청에서 호출하지 않는다. 따라서 Backend 개선을 크롤러 전체 개편 완료까지 미루지 않는다. 크롤러가 공개되어 있다면 관리 기능 차단은 Backend 과부하 방어와 함께 긴급 조치한다.

## 1. 착수 시 확인할 운영 조건

수정 전 기존 테스트 결과, 추천 점수/순서, 6,010개 카탈로그의 버전, 빌드 산출물을 기준으로 남긴다. 실제 배포 커밋과 설정도 확인한다. 로컬 소스가 운영에 그대로 배포됐다고 가정하지 않는다.

| 확인 항목 | 결정할 내용 |
|---|---|
| Railway의 실제 서비스·공개 도메인·실행 복제본 수 | 크롤러 공개 차단 대상, 프로세스 간 제한/잠금 필요 여부 |
| Vercel 및 사용자 정의 도메인 | 정확한 CORS 허용 목록과 프록시 경로 |
| Railway 직접 접근과 Vercel 경유 접근의 클라이언트 IP 전달 방식 | IP 제한이 우회되거나 모든 사용자가 한 IP로 묶이지 않도록 신뢰 프록시 범위 설정 |
| 예약 수집의 실행 주체·경로 | 상태 확인 GET을 수집 트리거로 사용하는 기존 스케줄을 인증된 작업으로 전환 |
| 인스턴스 CPU·메모리·정상 트래픽 | worker 수, 큐 크기, 호출량 제한과 성능 목표 최종 조정 |
| 비밀값 주입 방식과 기존 키 노출 여부 | 관리 키 설정, 불필요한 런타임 키 제거, 노출 확인 시 키 교체 |

이 항목들은 운영 반영 전에 확인한다. 로컬 코드 수정과 테스트 설계는 독립적으로 진행할 수 있다.

## 2. 단계별 작업과 공수

단일 개발자 기준 초기 추정은 **약 4~7 작업일**이다. 운영 접근, 의존성 업데이트 호환성, 실제 인스턴스 성능에 따라 조정한다. 달력상의 확정 완료일이나 성능 보장치가 아니다.

| 단계 | 예상 공수 | 주요 결과 |
|---|---|---|
| 운영 조건 확인 및 긴급 방어 | 0.5~1일 | 관리 경로 차단, 요청 제한, CORS 정리, 미사용 seed 경로 제거 |
| 추천 계산 구조 개선 | 1~2일 | 사전 계산 인덱스, worker 격리, 유한한 대기열 |
| 크롤러 구조·실패 처리 개선 | 1~2일 | 읽기/쓰기 분리, 입력 검증, 잠금·작업 큐·자원 반환 |
| 데이터·배포 방어 및 최종 검증 | 1.5~2일 | URL/스키마 검증, 의존성 감사, 헤더/컨테이너 강화, 배포·복구 검증 |

### 단계 A — 즉시 악용 범위를 줄인다

**F01: 요청 제한을 먼저 적용한다.**

- Backend의 추천 엔드포인트에 호출 빈도 제한과 전체 처리량 상한을 둔다. 일시적인 대량 요청에는 429와 Retry-After를 반환한다.
- 초기 설정 후보는 추천 IP별 분당 30회, 짧은 구간 연속 허용 3회다. 공용망 사용자의 정상 요청과 실제 유입량을 보고 조정하며, IP 제한만으로 분산 요청을 방어한다고 판단하지 않는다.
- 초기 제한 상태도 메모리를 무한히 쓰지 않도록 만료·최대 저장 항목 수를 둔다. 여러 인스턴스라면 공유 제한 저장소 또는 신뢰 가능한 진입 계층의 서비스 전체 제한을 적용한다.
- 신뢰할 프록시를 실제 구조에 맞춰 한정한다. 임의의 X-Forwarded-For 헤더를 신뢰하는 설정은 사용하지 않는다. Railway 직접 URL과 Vercel 경유 URL 양쪽에서 제한이 적용되는지 확인한다.
- 이 조치는 임시 과부하 방어다. 동기 연산 격리 완료 전에는 F01을 해결 완료로 처리하지 않는다.

**F02: 공개 크롤러 관리 기능을 닫는다.**

- 관리 HTTP 경로는 기본 비활성화하고 공개 인터넷 접근에서 제거한다. 운영상 필요한 경우에만 사설 경로에서 명시적으로 활성화한다.
- 활성화한 관리 기능에는 서버 측 비밀값을 필수로 요구한다. 관리 기능 활성 상태에서 키가 없으면 시작에 실패하도록 한다. 누락·잘못된 인증 요청에서는 DB 작업과 외부 요청을 시작하지 않는다.
- force 옵션은 인증된 관리 요청에만 허용하고 실행 중 잠금을 우회하지 못하게 한다.
- 현재 로컬/CLI 전용 크롤러라면 공개 서비스를 새로 만들지 않는다. CLI의 입력·큐·실패 처리 개선은 동일하게 적용한다.

**F07/C01: 불필요한 허용과 쓰기 경로를 제거한다.**

- Backend의 모든 vercel.app 허용 정규식을 삭제하고 소유한 운영/검증 origin만 정확히 등록한다. 프로덕션에서 허용 목록이 누락되면 배포 설정 오류로 처리한다.
- 현재 사용하지 않는 `/internal/seed-webtoons` 라우트와 선택적 HTTP seed 인터페이스를 제거한다. 기존 Supabase 적재 CLI는 별도 도구로 유지한다. 이에 맞춰 테스트 fixture·문서·환경 변수 예시를 정리한다.

완료 기준: 허용되지 않은 관리 요청은 401 또는 비활성 경로의 404이며 작업 시작 횟수는 0, seed 경로는 404, 추천 한도 초과는 429, 타인 Vercel origin에는 CORS 허용 헤더가 없다. 정상 도메인 및 같은 origin의 Vercel 프록시 호출도 검증한다.

### 단계 B — 추천 계산으로 다른 요청이 막히지 않게 한다 (F01)

- 카탈로그를 검증해 로딩할 때 ID 인덱스, 특징 벡터와 전체 카탈로그 기준 IDF를 한 번 생성한다. 요청마다 전체 벡터를 다시 만드는 경로를 제거한다.
- 추천 계산은 별도 worker에서 처리한다. worker 안에 카탈로그와 인덱스를 유지해 매 요청마다 대량 데이터를 복사하지 않는다. 메인 서버는 검증·작업 접수·응답을 담당한다.
- 초기 구성 후보는 인스턴스당 worker 1개, 대기 작업 최대 8개, 요청 전체 기한 5초다. 부하 시험에서 CPU·메모리·정상 응답 시간을 확인해 확정한다.
- 대기열 초과는 즉시 503으로 거부한다. 대기 요청 취소 시 큐에서 제거하고, 실행 중 작업이 기한을 넘으면 계산 자체를 중단하거나 worker를 교체한다. HTTP 응답만 끝내고 계산을 남기지 않는다.
- 카탈로그 버전 변경 시 인덱스를 다시 만든다. 준비되지 않은 인덱스로 트래픽을 받지 않도록 readiness와 프로세스 생존 상태 확인을 구분한다.
- 임의 excludeIds 조합을 무한 캐시하지 않는다. 추가 결과 캐시가 필요하면 카탈로그 버전을 키에 포함하고 용량·TTL을 제한한다.
- 추천 가중치, 전체 카탈로그 기준 점수, 동점 정렬, 플랫폼/완결 필터, 기존 추천 제외 및 후보 소진 동작을 유지한다.

완료 기준: 기존 기능 테스트 통과, 고정 입력의 추천 순서·이유 일치 및 점수의 사전 정의된 수치 오차 이내 일치, 처리량 상한 준수, 큐 초과 시 신속한 거부, worker 실패 이후 검색·health와 후속 추천 복구 확인.

성능 시험의 초기 목표는 동일한 6,010개 카탈로그와 명시한 시험 장비에서 워밍업 후 단일 추천 p95 500ms 이하, 추천 동시 요청 5개에서 health p95 100ms 이하로 둔다. 동일 환경에서 변경 전후를 비교하고, 운영 인스턴스의 실제 성능 목표는 별도로 확정한다. 대기 작업 수와 메모리가 설정된 범위에서 안정되는지도 확인한다.

### 단계 C — 크롤러의 읽기·쓰기와 자원 사용을 통제한다

**F02/F06: 공개 조회를 읽기 전용으로 만든다.**

- `/webtoons`에서 health-check self-call을 제거한다. health-check는 저장된 상태만 반환하며 갱신을 실행하지 않는다.
- 공개 단건 조회에서 실시간 enrich 및 persist 기능을 제거한다. 저장된 메타데이터만 반환하고 보강은 인증된 작업/CLI로 수행한다. 기존 관련 쿼리는 명시적으로 거부하고 API 문서를 갱신한다.
- 예약 수집을 새 관리 경로 또는 CLI로 전환한다. 기존 스케줄러와 운영 스크립트도 함께 수정해 갱신이 중단되지 않게 한다.
- 이 구조에서는 공개 조회를 위한 외부 API 캐시가 필수가 아니다. 관리자 보강 작업은 같은 작품에 대한 중복 작업을 합치고 전체 실행 기한을 둔다.

**F03: 값의 실제 타입과 범위를 검증한다.**

- 쿼리를 단일 문자열로 파싱한 뒤 유한한 정수인지 검사한다. 배열·객체·중복 파라미터, 음수·0·소수·NaN·Infinity는 DB 접근 전에 거부한다.
- 목록 크기는 1~100, 보강 배치 건수는 1~500으로 제한한다. page와 offset 계산에는 안전한 정수 및 상한 검증을 적용한다.
- 보강 간격은 서버가 정한 최소 간격을 강제한다. 초기안은 200~5,000ms이며 플랫폼에 필요한 더 긴 간격은 유지한다. 사용자 입력이 서버 최소 간격을 낮추지 못하게 한다.
- boolean, provider, sort, 요일도 허용 값만 받는다. 문자열 false를 참으로 처리하는 동작도 함께 바로잡는다.

**F04/F05: 작업 수명과 실패를 관리한다.**

- 방치되는 비동기 즉시 실행 함수를 작업 관리자/큐로 교체한다. 요청 접수는 202와 작업 ID를 반환하고, 완료·실패 상태는 관리 경로에서 확인한다. 중복 실행 요청은 409로 거부한다.
- 플랫폼별 중복 실행 잠금과 SQLite 쓰기 직렬화를 적용한다. 전역 쓰기 동시성은 1로 시작한다. 여러 프로세스가 같은 데이터에 접근한다면 원자적인 공유 잠금을 사용하며, 프로세스 메모리 잠금만으로 완료 처리하지 않는다.
- 외부 수집은 DB 트랜잭션 밖에서 수행하고, 검증된 결과를 저장할 때만 짧게 트랜잭션을 연다. start/commit/rollback/release 각각의 실패를 다루고 작업 잠금은 finally에서 반환한다.
- setInterval 폴링을 고정 수의 실행 슬롯을 가진 큐로 교체한다. 성공·실패·취소 시 슬롯을 반환하고 플랫폼별 큐 크기, 최소 요청 간격, 전체 작업 기한을 강제한다.
- 외부 요청의 개별 timeout과 재시도 총예산을 둔다. 지연·연속 실패 시 새 작업을 멈추고 과도한 재시도를 방지한다. 실행이 끝나지 않은 작업의 잠금만 풀어 중복 실행되는 상황을 막는다.
- Express 라우트 오류를 공통 오류 처리기로 전달한다. 전역 unhandledRejection을 무시해 프로세스를 계속 돌리는 방식으로 문제를 숨기지 않는다.

완료 기준: 조회 1회당 외부 호출·DB 쓰기 0, 비정상 입력에서 DB 접근 0, 동일 플랫폼 중복 작업 1개 이하, 전체 DB 쓰기 동시성 1 이하, 실패 후 잠금/슬롯 반환, 작업 종료 후 남는 수집 타이머 0, DB·외부 API 오류 주입 시 미처리 Promise 거부 0.

### 단계 D — 데이터·브라우저·배포 방어를 완성한다

**C02: 데이터 스키마와 URL 경계를 검증한다.**

- Backend 카탈로그 로딩과 수집/동기화 경계에서 필드 타입, 문자열 길이, 배열 길이, ID 중복, 허용 provider를 검사한다. 기존 데이터의 최대 길이를 측정한 뒤 정상 작품을 누락시키지 않는 상한을 정한다.
- 작품 URL은 플랫폼별 정확한 HTTPS hostname과 허용 경로/ID를 검증한다. URL 파서로 검사하며 사용자 정보가 포함된 URL, 비표준 포트, javascript/data 프로토콜, 유사 도메인을 거부한다.
- 이미지는 승인된 CDN hostname만 허용한다. 카카오페이지를 추후 포함할 경우 새 정상 도메인을 명시적으로 등록한다.
- Frontend에서 API 응답을 런타임 검증하고, 비정상 링크·이미지는 표시하지 않는다. 오류 데이터가 화면 전체를 중단시키지 않도록 처리한다.
- 카탈로그 변경은 임시 파일 검증 후 원자적으로 반영한다. 실패하면 직전의 검증된 카탈로그를 유지하고 이유를 기록한다.

**F07 및 브라우저 방어: 배포에 맞춰 헤더를 설정한다.**

- CSP, frame-ancestors, X-Content-Type-Options, Referrer-Policy, Permissions-Policy를 설정한다. API에도 적절한 응답 헤더와 상세 내부 오류 비노출을 적용한다.
- CSP는 먼저 Report-Only로 정상 요청을 확인한 후 강제한다. 현재 화면의 동적 스타일·WebGL·이미지·폰트·API 연결에 필요한 최소 허용만 설정한다. 화면을 깨뜨리는 정책을 바로 적용하지 않는다.
- 실제 호스팅의 HTTPS/HSTS와 헤더를 확인한다. 하위 도메인 전체 정책은 실제 도메인 구성을 확인한 뒤 결정한다.

**의존성·실행 환경:**

- 레지스트리에 연결 가능한 환경에서 세 프로젝트의 잠금 파일과 실제 설치 트리 전체를 감사한다. 런타임과 개발 전용 의존성을 구분하고 공격 경로가 있는 문제부터 수정한다.
- 특정 과거 CVE의 최소 수정 버전만 목표로 삼지 않는다. 구현 시점의 공식 보안 공지를 확인해 유지보수되는 버전을 선택하고, 잠금 파일과 호환성 테스트를 함께 갱신한다.
- 잠금 파일에 맞는 고정 설치를 적용한다. Backend Docker 빌드/실행 단계의 npm install은 npm ci로 바꾸고, 크롤러는 실제 Yarn 버전에 맞는 잠금 파일 고정 설치를 사용한다.
- 컨테이너를 비특권 사용자로 실행한다. 추천 서버의 카탈로그는 읽기 전용으로 두고 크롤러 SQLite는 별도 쓰기 볼륨으로 관리한다.
- 추천 서버에 불필요한 Supabase 쓰기 키가 배포되어 있다면 제거하고 적재 작업 환경에만 둔다. 키의 노출 이력이 확인되면 교체·폐기까지 수행한다. 로그에는 비밀값·인증 헤더를 남기지 않는다.

완료 기준: 기존 6,010개 정상 데이터 모두 통과, 악성/비정상 fixture 거부, 프론트 검색·추천·이미지·WebGL 기능 정상, 컨테이너 비특권 실행 확인. 실제 공격 경로가 있는 높음/치명적 의존성 문제가 남으면 배포 완료로 처리하지 않고 차단·제거·수정한다. 도달하지 않는 공지는 근거와 추후 재검토 조건을 기록한다.

## 3. 검증 및 회귀 방지

기존 재현 스크립트는 취약 동작이 존재함을 기대하므로 수정 완료의 통과 기준으로 그대로 사용할 수 없다. 감사 당시 결과는 보존하고, 보완 작업에는 다음의 **안전한 동작을 기대하는 테스트**를 추가한다.

| 검증 대상 | 통과 조건 |
|---|---|
| 추천 과부하 | 인덱스 재계산 횟수 제한, worker/큐 상한 준수, 429/503, 취소·기한 초과 후 계산/큐 정리 |
| 추천 기능 회귀 | 점수·순서·이유, 필터, 재검색 제외, 후보 소진, 전체 카탈로그 기준 IDF 유지 |
| 인증/잠금 | 누락·오류 키 거부 및 부작용 0, 비밀값 미설정 시 관리 기능 시작 실패, 중복 실행 거부 |
| 페이지·배치 검증 | 정상 경계값 통과, 음수·0·소수·배열·객체·중복·비유한 값 거부 |
| 읽기 전용 경로 | 목록·단건·health 조회에서 외부 요청과 쓰기 모두 0 |
| 실패 처리 | DB 조회/시작/저장/commit/rollback/release 및 네트워크 실패 주입, 오류 응답·작업 실패 기록·자원 반환 확인 |
| 자원 누수 | 반복 완료/실패/취소 후 활성 타이머·슬롯·대기 작업 수가 기준으로 복귀 |
| 데이터/URL | 신뢰 도메인과 정상 레코드는 통과, 피싱·잘못된 스킴·비정상 필드 거부 |
| 실제 HTTP/프록시 | JSON 파서부터 라우트까지 통합 테스트, 두 진입 경로에서 IP 위조 방지와 호출량 제한 |
| 배포 | 빌드/기존 테스트 통과, 실제 응답 헤더·인증·health 확인, 예약 작업 정상 완료 |

외부 API와 DB 오류 주입은 대역/격리 DB로 검증한다. 부하 시험은 로컬 또는 별도 검증 환경에서 상한을 정해 실행한다. 운영에서는 소수의 정상 조회와 인증 거부 확인만 수행한다.

## 4. 배포 순서와 복구

1. 현재 배포 버전·설정과 SQLite/카탈로그를 백업하고, 운영 환경 변수의 존재만 확인해 비밀값을 노출하지 않는다.
2. 공개된 크롤러 관리 경로를 먼저 접근 제한한다. Backend의 요청 제한·CORS/seed 정리도 독립 배포할 수 있게 나눈다.
3. 추천 계산 개편을 검증 환경에서 배포해 준비 시간·메모리·성능·동작 동등성을 확인한 뒤 Backend에 반영한다.
4. 크롤러의 관리 인증·작업 상태 API와 스케줄러를 함께 전환한다. 읽기 전용 health와 예약 수집이 각각 정상인지 확인한다. 이전 무인증 경로를 호환 목적으로 남기지 않는다.
5. 데이터 검증과 프론트 변경, 의존성·컨테이너 강화 및 CSP를 검증 후 순차 적용한다. 데이터 스키마 변경이 필요하면 구버전 호환/복구 절차를 먼저 마련한다.
6. 배포 직후 오류율·지연·429/503·메모리·이벤트 루프 지연·작업 대기 수를 집중 확인하고, 이후 정상 수집 주기까지 최소 한 번 관찰한다.

정상 사용자 요청 실패·지연의 급증, 카탈로그 로딩 실패, 예약 수집 실패 또는 지속적인 메모리 증가가 있으면 해당 변경을 복구한다. 복구 시에도 관리 경로 비공개와 호출량 제한은 유지한다. 인증 없는 과거 배포로 통째로 되돌려 취약점을 다시 열지 않는다. 임시로 추천 요청을 제한하고 검색을 제공하는 방식으로 가용성을 유지할 수 있다.
