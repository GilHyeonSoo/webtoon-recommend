# 웹툰 추천 보안 보완 결과

최종 검증일: 2026-11-07 (Asia/Seoul)

추천 서버·크롤러·프론트엔드의 보안 보완과 로컬 검증을 마쳤다. 총 40개 테스트가 통과했고, 세 프로젝트의 전체 의존성 감사에서 알려진 취약점은 0건이었다. 운영 서비스 배포와 사설망·프록시·예약 수집 설정은 별도로 반영해야 한다.

## 재개 후 마무리한 수정

중단 직전에 추가한 worker 취소 기능을 검증하면서 복구 타이머 참조가 남아 다음 장애의 자동 복구가 예약되지 않을 수 있는 결함을 수정했다. 활성 작업 취소는 공유 플래그로 계산에 전달해 인덱스를 보존하고, 취소에 응답하지 않는 작업은 기한에 맞춰 종료한다. 대기 중 취소는 즉시 큐 용량을 반환한다. 반복 시간 초과와 그 사이의 명시적 준비 이후에도 자동 복구되는 테스트를 추가했다.

프론트엔드는 카탈로그 입력과 실제 API 응답을 구분해 필수 배열이 없는 응답을 거부한다. 잘못된 응답이 표지·작가·장르 렌더링까지 전달되어 화면 오류를 만드는 경로를 차단했다.

새 크롤러 export 배치가 요구하는 보강 결과 API도 연결했다. 기존 `enrichWebtoonMeta`의 작품 반환 형식은 유지하면서 성공 여부·HTTP 상태를 별도 함수로 제공한다. 작업 취소가 일반 보강 실패로 바뀌지 않고 상위로 전파되는 테스트도 통과했다. 기존 화면·크롤러 콘솔·SEO 작업의 변경은 보존했다.

HTTP 시험은 loopback 서버, DB 시험은 임시 SQLite를 사용했다. 운영 데이터와 외부 플랫폼 API에 공격·수집·쓰기 요청을 보내지 않았다. 프론트엔드는 병행 변경으로 빌드 산출물이 교체되는 영향을 피하기 위해 검증용 소스 스냅샷을 사용했다. 검사한 주요 소스와 잠금 파일의 해시는 `remediation-validation-2026-11-07.json`에 기록했다.

## 추천 성능

Node.js v24.10.0, 작품 6,010개, 로컬 환경에서 기준 계산과 worker 응답의 세 가지 입력 결과가 완전히 일치했다. 응답 18회와 동시 요청 5개를 포함한 제한된 시험 결과다. 호출량 제한은 별도 HTTP 테스트로 검증하고 성능 측정에서는 비활성화했다.

| 측정 | 결과 |
|---|---|
| 요청마다 인덱스를 만드는 기준 계산 3회 | 약 2.01~2.52초 |
| 인덱스 준비 시간 | 약 2.27초, HTTP 접수 시작 전에 수행 |
| 개선한 추천 HTTP 응답 p95 | 약 295ms |
| 추천 동시 처리 중 health 응답 p95 | 약 9.7ms |

호스트 부하와 장비 성능에 따라 수치는 달라진다. 2026-10-16의 약 176ms 측정은 별도 과거 기록이며 이번 결과와 동일한 시험 시점으로 취급하지 않았다. 운영 처리량이나 대규모 분산 공격 방어 성능을 측정한 결과는 아니다.

## 의존성 보완

재개 시점에 새로 공개된 공지도 반영했다. Backend와 크롤러의 `body-parser`는 1.20.9로 갱신했고 `qs`도 취약 범위를 벗어나는 버전으로 갱신했다. 크롤러의 glob·minimatch는 Node 호환 범위를 확인한 수정 버전으로 한정 교체했다. TypeORM을 강제 다운그레이드하지 않았으며 교체 후 HTTP·DB 테스트와 전체 타입 검사를 수행했다.

glob 14.0.2와 minimatch 11.0.1을 하위 의존성 override로 지정한 이유는 각각 공개된 취소 처리 및 패턴 증폭 문제다. 유지보수 시 상위 패키지가 수정 버전을 채택하면 override 필요성을 재검토한다. [glob 보안 공지](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4), [minimatch 보안 공지](https://github.com/advisories/GHSA-g3hv-75wg-m249).

감사 0건은 검사 시점에 공개된 의존성 공지 기준이다. 애플리케이션의 모든 취약점이 없다는 보장은 아니다.

## 운영 반영이 필요한 항목

1. 실제 운영 origin과 신뢰 프록시 IP/CIDR을 확인하고 Backend를 배포한다. 현재 호출 제한은 프로세스별이므로 여러 인스턴스라면 서비스 전체의 제한도 추가한다.
2. 크롤러를 사설 서비스로 유지하고 관리 비밀값을 서버 환경에 주입한다. 기존 health-check 수집 스케줄을 인증된 작업 실행 스크립트로 전환한다.
3. Vercel에 보안 헤더를 반영한 뒤 정상 화면과 Report-Only CSP를 확인하고 전체 CSP 강제 범위를 확정한다.
4. Docker 실행 환경에서 비특권 실행과 카탈로그 읽기 전용 권한을 검증한다. 이번 환경에는 Docker CLI가 없어 이미지 실행까지 확인하지 않았다.
5. 실제 배포의 오류율·429/503·작업 대기 수·메모리·수집 주기를 관찰한다. 무인증 관리 경로를 다시 공개하지 않는 복구 절차를 유지한다.

배포·환경 변수·복구 절차는 같은 폴더의 `deployment.md`에 있다. 이번 작업의 완료 범위는 코드 보완과 위의 로컬 검증이며, 운영 배포·키 교체·사설망 설정은 실행하지 않았다.
